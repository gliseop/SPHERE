# Ревью коммита `4a68dcc` — MAGISTRY-LC greenfield

## Общая оценка

Реализация покрывает милестоуны M0–M3 из плана: типизированные ID, EntityRegistry, гибридный арбитр, движок с параллелизмом агентов, DAO-голосования, WorldComposer, ViolationOracle, CLI. Код чистый, хорошо декомпозирован, тесты проходят (548/548). Ниже — замечания по степени критичности.

---

## Критичные проблемы

### 1. Память агента — плоский список строк, а не гибридный индекс

`state.py:30-31` — `memory_summary: str` + `memory_events: list[str]` — это не то, что обсуждалось в плане. По плану память — двухслойная: ConversationSummaryBufferMemory (рабочий буфер) + гибридный индекс (embeddings + BM25) для долгосрочных фактов. Сейчас это обрезанный `list[-200:]` без суммаризации, без поиска по релевантности, без embeddings. В эксперименте S2/G2 именно отсутствие обратной связи и суммаризации приводило к зацикливанию (12x одно действие). `engine.py:334-355` (`_update_agent_memory`) просто дописывает строки в список — нет LLM-суммаризации старых фактов.

### 2. Персона агента — одна строка `persona: str`

`config.py:84` — персона сведена к одной строке. В плане обсуждалась трехслойная архитектура PersonaLibrary → PersonaGenerator → WorldComposer с биографиями в 1000–2000 слов и интервью из 30 вопросов. Сейчас `WorldComposer` генерирует только `persona: str`, что фактически возвращает проблему однотипных профилей, зафиксированную в Park et al.

### 3. Арбитр не ведет YAML-журнал как долгоживущий контекст

`arbiter.py:387-394` — YAML-журнал передается в каждый `perform`-вызов заново через `state.journal_yaml()`. Это воспроизводит проблему S2/G2: арбитр получает полный дамп на каждое действие. Из плана: «арбитр ведёт YAML-документ инкрементально, не пересоздаёт на каждый вызов». Текущая реализация — пересоздает каждый раз.

## Существенные замечания

### 4. Нет Capability (полномочий) — любой агент может делать всё

`config.py:85` — `capabilities: list[str]` хранится в конфиге, но нигде не проверяется при арбитраже. Агент без capability `audit` может создавать аудиторские дела, агент без `dao` может голосовать. Арбитр (`arbiter.py`) не обращается к `agent.capabilities` ни в одном месте.

### 5. LangGraph-интеграция формальна

`graphs.py` — граф из 2 нод (`gather_actions` → `apply_actions`) без чекпоинтов, без условных переходов, без SqliteSaver. Из плана: «чекпоинты через SqliteSaver — можно остановить и возобновить симуляцию с любого раунда». Текущий граф — это обертка над двумя вызовами, не дающая преимуществ перед обычным asyncio-циклом в `engine.py`.

### 6. `_gather_actions` — неидиоматичный параллелизм

`engine.py:256-260` — задачи создаются через `create_task`, результаты собираются ручным циклом `for t in tasks: await t`. `asyncio.gather` был бы идиоматичнее и надежнее. Сам по себе параллелизм корректен: `LLMCaller` оборачивает синхронные вызовы через `asyncio.to_thread`, что дает реальный параллелизм на I/O.

### 7. `_apply_actions` — арбитраж perform делается последовательно

`engine.py:275-276` — `perform`-действия вызывают LLM, но арбитраж идет последовательно по агентам. Для N агентов с perform — это N последовательных LLM-вызовов. Арбитраж structured-действий детерминированный и не требует LLM, но perform требует. Это бутылочное горлышко.

### 8. Утечка всех ID в промпт агента

`agent.py:64`:

```python
chan_ids = ", ".join(sorted(state.registry.list_ids()))
```

Агенту передается полный реестр (agents + channels + orgs + work_items + votes + artifacts). Это (а) раздувает промпт, (б) дает агенту информацию, которую он не должен знать (внутренние vote ID, artifact ID). По плану: «минимальный контекст — только наблюдения, контакты и доступные действия».

### 9. Отсутствует проверка `wants_promotion`

`config.py:87` — `wants_promotion: bool` хранится, но `dao.py` не использует это поле. Агент, не желающий повышения, может быть номинирован и одобрен через DAO.

## Мелкие замечания

### 10. Дублирование `chan:public`

`engine.py:159-167` — движок всегда создает `chan:public`, а `lc_minimal.yaml` тоже содержит `chan:public` в `world.channels`. Дублирование перехватывается через `try/except pass` (строка 181), но это тихо глотает ошибку.

### 11. `ActionResult.ops: list[object]` — потеря типизации

`arbiter.py:60` — ops хранятся как `list[object]`, хотя все элементы — конкретные dataclass (SendMessageOp, CreateWorkItemOp и др.). В `_apply_ops` потом `op.apply(state)  # type: ignore[attr-defined]`. Протокол `StateOp` определен в `ops.py`, но не используется для типизации.

### 12. `_op_from_llm` — тихий `continue` при ошибке

`arbiter.py:416-417`:

```python
except Exception:
    continue
```

Если LLM вернул невалидный op — он тихо пропускается. Нет логирования, нет события в EventLog. Действие будет «одобрено», но часть ops может быть потеряна.

### 13. `ScenarioConfig` — frozen по духу, mutable по факту

`composer.py:168-169`:

```python
cfg.runtime.language = language
```

После создания `ScenarioConfig` через конструктор, поля перезаписываются напрямую. Это работает, но `extra="forbid"` не защищает от мутации. Если позже конфиг станет immutable (frozen), такой паттерн сломается.

### 14. Нет seed (воспроизводимость)

`config.py:172` — `seed: int = 42` хранится, но нигде не передается в LLM. Параметр `temperature=0.0` в сценарии дает псевдодетерминизм, но при `temperature > 0` воспроизводимость теряется полностью. В `engine.py` seed не используется для порядка агентов или генерации ID (хотя ID-аллокатор детерминирован по порядку вызовов).

### 15. Приватные сообщения утекают в world-gen

`worldgen.py:50` — `compact.append({"event_type": ..., "actor_id": ..., "payload": ev.payload})` — payload может содержать приватные сообщения между агентами. Из плана: «world-gen не видел промпты/ответы» — промпты действительно не утекают, но содержимое приватных сообщений (text) попадает в world-gen через payload.

### 16. `EventLog.iter_events` — непоследовательный тип возврата

`events.py:84-97` — `iter_events` возвращает `Iterable[Event]`, но при пустом файле возвращает `[]` (список), а при непустом — генератор. Тип возврата непоследователен. Кроме того, файл остается открытым на всё время итерации (генератор держит контекстный менеджер).

## Что хорошо

- Антифантомы работают (тест подтверждает): `arbiter_rejected` на `agent:phantom`.
- Четкое разделение Action → StateOp → Event. Операции детерминированны, LLM используется только для `perform`.
- DAO-логика (`dao.py`) компактна, детерминированна и полна: quorum, threshold, consent.
- Трассировка LLM отделена от EventLog — промпты не утекают в мир.
- Тесты smoke-уровня с MockLLMProvider — можно запускать без ключей API.
- ID-аллокатор с `tick_N` — детерминированный и читаемый.
