# Дизайн: Веб-интерфейс для лайв-исследований в форме графа

Дата: 2026-02-22

## Контекст

MAGISTRY — агентно-имитационная симуляция гибридных систем управления. В ходе прогона агенты (чиновники `off_*`, подрядчики `biz_*`, аудиторы `aud_*`) взаимодействуют по раундам: открывают дела, обмениваются сообщениями, подают предложения. Симуляция ведёт журнал событий в формате JSONL (`results/*_events.jsonl`). Социальный граф связей строится из событий `graph_updated` и `message_sent`.

Цель интерфейса — дать исследователю возможность наблюдать за развитием социального графа как в режиме воспроизведения завершённых прогонов, так и в режиме мониторинга текущего прогона.

## Архитектура решения

Выбран Подход C: минимальное изменение в ядре (streaming append в EventLog) + автономный веб-сервер с file watcher. Симуляция не переписывается и не усложняется.

### Изменения в ядре симуляции

Единственное изменение — добавление `set_stream_path(path: Path)` в `EventLog`. При вызове метод сохраняет путь; последующие вызовы `log()` дозаписывают каждую строку в файл (режим `a`). Это позволяет читать события из файла сразу в ходе прогона.

В `run_research.py` перед `env.run()` добавляется одна строка:
```python
env.state.event_log.set_stream_path(events_path)
```

### Backend (FastAPI)

| Эндпоинт | Тип | Назначение |
|---|---|---|
| `GET /api/runs` | REST | Список доступных `*_events.jsonl` с метаданными |
| `GET /api/run/{name}` | REST | Все события прогона в JSON |
| `WS /ws/playback/{name}?speed=2.0` | WebSocket | Воспроизведение с заданной скоростью |
| `WS /ws/live` | WebSocket | Мониторинг текущего прогона (file watcher, интервал 0.5 сек) |

#### WebSocket-протокол (сервер → клиент)

```json
{ "type": "meta",   "scenario": "S1", "governance": "G2", "max_rounds": 8 }
{ "type": "event",  "data": { ...Event } }
{ "type": "graph_state", "nodes": [...], "edges": [...] }
{ "type": "done" }
```

Сервер реконструирует состояние социального графа из событий `graph_updated` и периодически отправляет `graph_state` клиенту (при каждой смене раунда).

### Frontend (React + Vite)

#### Компоновка

Трёхколоночный layout:
- **Левая панель**: RunSelector (список прогонов), переключатель Live/Playback, PlaybackControls (ползунок скорости 0.5x–10x, Play/Pause/Step)
- **Центр**: граф (react-force-graph-2d), строка состояния внизу
- **Правая панель**: EventFeed (прокручиваемая лента), AgentPanel (при клике на узел)

#### Граф

Узлы — агенты. Цветовое кодирование по роли: `off_*` → красный, `biz_*` → синий, `aud_*` → оранжевый. Размер узла пропорционален текущей репутации (из событий `reputation_changed`; если таковые отсутствуют — одинаковый размер).

Рёбра строятся из `graph_updated`. Толщина ребра пропорциональна накопленной силе связи. Рёбра с силой ≥ 3.0 подсвечиваются красным как подозрительные. Рёбра от `message_sent` с `private=true` — пунктирные, публичные — сплошные; гаснут через 3 раунда.

При появлении нового события на узле-источнике — кратковременная анимация пульса.

#### Строка состояния

Раунд: N/M, Событий: K, Приватных сообщений: XX%, Нарушений: Z

## Обоснование ключевых решений

**file watcher вместо WebSocket-интеграции в Environment.** Изменения в ядре симуляции рискованны: они могут сломать тесты, нарушить воспроизводимость или усложнить поддержку. File watcher обеспечивает ту же функциональность без изменения контракта Environment.

**react-force-graph-2d, а не D3.js напрямую.** Библиотека строится поверх D3 и предоставляет React-совместимый компонент с canvas-рендерингом — значительно быстрее SVG при большом числе узлов и событий.

**WebSocket-протокол с типом `graph_state`.** Клиент не занимается реконструкцией графа из событий — сервер отдаёт готовое состояние при каждой смене раунда. Это упрощает логику фронтенда и делает состояние предсказуемым.

## Компоненты не входящие в scope

- Аутентификация и мультипользовательский доступ
- Редактирование конфигурации прогона из интерфейса
- Сохранение аннотаций исследователя
- Мобильная версия
