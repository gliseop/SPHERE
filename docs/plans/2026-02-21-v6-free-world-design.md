# MAGISTRY v6: свободные агенты в свободном мире

## Цель

Убрать привязку симуляции к конкретным организационным процессам (закупки, наём, бюджет) и дать агентам возможность действовать свободно в рамках правдоподобной организации. Арбитр контролирует правдоподобность вместо жёсткого конечного автомата. LLM-оракул определяет нарушения постфактум.

## Обоснование

Результаты первого исследовательского прогона v5 показали фундаментальную проблему: за 15 раундов агенты создали всего 1 дело. Они пытались «жить» — организовывать обучение, внедрять бизнес-правила, проводить аудит — но жёсткий реестр типов дел (CASE_REGISTRY) и конечный автомат стадий отклоняли всё, что не укладывалось в 4 зашитых типа: procurement, hiring, budget, investigation. Арбитр корректно отклонял 24% действий, но проблема была не в агентах, а в системе.

Текущая архитектура, унаследованная от v4, моделирует конкретный бизнес-процесс (тендерные закупки) с конкретными ролями (заказчик, подрядчик, аудитор). Исследовательская задача MAGISTRY шире: моделирование организационной коррупции в произвольных процессах. Привязка к закупкам ограничивает и разнообразие поведения агентов, и типы нарушений, которые можно обнаружить.

## Архитектурные решения

### Дела без реестра типов

CASE_REGISTRY удаляется полностью. Дело (Case) сохраняет структуру — тип, стадия, владелец, описание, — но тип и стадия становятся произвольными строками. Агент может создать дело с типом «обучение», «аттестация», «инвентаризация» или любым другим. Арбитр оценивает правдоподобность создания дела в контексте организации и роли агента, а не по реестру допустимых типов.

Переходы между стадиями также контролирует арбитр. Вместо FSM-правила «procurement: open -> collecting -> evaluation -> closed» арбитр решает, логичен ли переход «подготовка -> согласование» для дела типа «обучение» в данной организации. Это увеличивает нагрузку на LLM-арбитра, но снимает ограничения на типы деятельности.

### Операции состояния

16 текущих операций (create_case, close_case, transfer_funds, send_message, add_evidence и другие) остаются как базовый набор. Они достаточно абстрактны для поддержки произвольных процессов. Изменения:

- `create_case`: не обращается к CASE_REGISTRY, принимает произвольный тип.
- `close_case`: не проверяет terminal_stages, арбитр решает, можно ли закрыть дело.
- `submit_proposal`: работает с любым типом дела, не только с procurement.
- `initiate_tribunal`: создаёт дело типа «расследование», но без привязки к конкретному хардкоду auditor/investigation.
- Все модели операций переходят на `extra="ignore"` вместо `extra="forbid"`, чтобы LLM мог передавать дополнительные поля без ошибок валидации.

### Гибридные сценарии

Сценарий состоит из двух частей: структурных параметров и нарративного контекста.

Структурные параметры определяют воспроизводимые характеристики: количество агентов, уровень коррупционного давления (0.0 — чистая организация, 1.0 — тотальная коррупция), режим управления (G0-G3), количество раундов. Эти параметры при фиксированном seed обеспечивают воспроизводимость эксперимента.

Нарративный контекст — текстовое описание типа организации, которое генератор мира развивает в конкретные детали: отделы, должности, текущие процессы, потребности. Это описание обеспечивает разнообразие организаций при одних и тех же параметрах.

Пример:
```
S0: corruption_level=0.0, agents=5, narrative="муниципальная администрация среднего города"
S1: corruption_level=0.5, agents=5, narrative="муниципальная администрация среднего города"
S2: corruption_level=0.8, agents=7, narrative="региональное управление строительства"
```

Генератор мира, получив narrative и seed, создаёт конкретных людей с должностями, личностными чертами, межличностными связями и текущими задачами. Уровень коррупции определяет, сколько агентов получат высокие значения жадности и низкие значения честности.

### Генератор мира

Генератор мира получает расширенную роль. Помимо генерации агентов с личностями, он создаёт описание организации (organization_description), которое включает:

- Название и тип организации
- Организационная структура (отделы, иерархия)
- Основные процессы и регламенты
- Текущие задачи и потребности
- Нормативная база (что считается нарушением)

Это описание передаётся арбитру как контекст для оценки правдоподобности действий. Оно также доступно агентам через контекстную информацию.

### Арбитр

Системный промпт арбитра (WORLD_RULES) переписывается. Вместо перечисления конкретных типов дел и стадий арбитр получает: общие принципы организационной деятельности, описание организации от генератора мира, список доступных операций с семантикой. Арбитр оценивает каждое действие по критериям: правдоподобно ли для роли агента, согласуется ли с текущим состоянием дел, не нарушает ли физических или логических ограничений.

### LLM-оракул

Новый компонент, заменяющий эвристический ViolationClassifier. После завершения симуляции оракул получает полный лог событий, включая приватные сообщения между агентами (к которым аудитор внутри симуляции не имеет доступа). Оракул анализирует все события и классифицирует, какие действия представляют собой нарушения: взятки, сговор, фаворитизм, подделка документов, злоупотребление полномочиями.

Результат оракула — ground truth для метрик. Сравнение с выводами аудитора внутри симуляции даёт F1, precision, recall.

### Метрики

- **F1 / precision / recall**: по сравнению результатов аудитора с оракулом.
- **action_diversity**: количество уникальных типов действий (чем больше, тем богаче поведение).
- **case_diversity**: количество уникальных типов дел (новая метрика).
- **arbiter_rejection_rate**: доля отклонённых арбитром действий (должна снизиться после снятия ограничений).
- **corruption_rate**: доля нарушений из всех действий (по оракулу).
- **detection_rate**: доля обнаруженных нарушений (по аудитору).
- **scheme_depth**: глубина коррупционных схем (по графу связей).
- **activity_volume**: общее количество дел и действий за симуляцию.

## Компоненты и изменения

### Удаляемые компоненты

- `cases.py`: CASE_REGISTRY, CaseSchema, validate_transition, check_condition — весь FSM-механизм.
- `classifier.py`: ViolationClassifier с эвристиками по приватным сообщениям — заменяется оракулом.

### Существенно переписываемые

- `scenarios.py`: новая модель сценария с narrative_context и corruption_level.
- `world_rules.py`: WORLD_RULES без привязки к конкретным процессам.
- `world_generator.py`: генерация описания организации.
- `context.py`: убрать хардкод investigation/tribunal, показывать описание организации.
- `environment.py`: убрать FSM-переходы, локации из генератора мира.
- `metrics.py`: F1 по оракулу вместо эвристик.

### Умеренно изменяемые

- `state_ops.py`: убрать проверки CASE_REGISTRY, `extra="ignore"`.
- `tools/actions.py`: убрать проверки case_type, deadline-логику для procurement.
- `cognitive_runner.py`: обобщить описания инструментов.
- `agents.py`: обобщить описания возможностей, убрать хардкод archetype_action_patterns.
- `arbiter.py`: расширить контекст описанием организации.

### Новые компоненты

- `oracle.py`: LLM-оракул для определения нарушений постфактум.
