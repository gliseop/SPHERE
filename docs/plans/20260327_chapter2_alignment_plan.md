# План выравнивания проекта со второй главой ВКР

## Цель документа

Документ фиксирует план приведения текущего состояния SPHERE к содержательным требованиям [chapter_2.md](C:/Users/Administrator/Documents/MAGISTRY/chapter_2.md).

План опирается на уже проведённое сравнение главы 2 с:

- кодом движка `sphere_lc`;
- web/backend логикой режимов управления;
- сценариями и seed-конфигурациями;
- тестами, проверяющими persona, worldgen, runtime-аудит, truth/evaluation и fidelity.

## Исходный вывод

На текущий момент проект хорошо совпадает с главой 2 на уровне общего архитектурного каркаса:

- есть дискретный tick-engine;
- есть typed-id и антифантомная защита;
- есть environment-layer;
- есть runtime-аудитор;
- есть deterministic truth-layer, evaluation и fidelity;
- есть persona/interview memory pipeline;
- есть сценарная конфигурация и воспроизводимый apply-цикл.

Однако есть ряд существенных расхождений между текстом главы и фактической реализацией:

- семантика режимов `G0–G3` расползлась между thesis/runtime/web;
- action-модель стала гибридной (`structured + perform`), а не чисто freeform;
- создание новых акторов допускается не только через worldgen;
- коммуникация в коде permission-gated, хотя в главе описана как универсальная;
- spatial grounding частично soft-prompted, а не жёстко enforced;
- persona pipeline в рантайме не совпадает буквально с описанной трёхступенчатой схемой;
- anonymity коллегиального review нарушается раскрытием состава reviewers;
- есть текущие регрессии в chapter-critical путях, уже проявляющиеся в тестах.

## Ключевая развилка перед внедрением

До начала правок нужно зафиксировать источник истины для каждого расхождения.

Есть два варианта:

1. Код приводится к главе 2.
2. Глава 2 переписывается под текущую реализацию.

Рекомендуемый вариант: смешанный.

- Для экспериментально значимых контуров source of truth должна быть глава 2.
- Для инженерных эволюций, которые повышают проверяемость и не ломают исследовательскую логику, допустимо обновить текст главы и техдоков, а не откатывать код назад.

Практически это означает:

- `G0–G3`, anonymity review, spatial constraints, truth/evaluation и regression-fixes надо выравнивать под главу;
- формулировки про action-модель и persona pipeline нужно пересмотреть после отдельного решения, что в проекте считается финальной исследовательской архитектурой.

## 2. Нормализация семантики `G0–G3`

### Цель

Сделать так, чтобы thesis, runtime, web presets, seed-сценарии и UI трактовали режимы управления одинаково.

### Целевая таблица

- `G0`: аудит выключен.
- `G1`: аудит включён, но без freeze и без collegial review.
- `G2`: аудит включён, freeze включён, collegial review выключен.
- `G3`: аудит включён, freeze включён, collegial review включён.

### Задачи

- Решить судьбу `reputation_penalty_delta`: либо удалить как ложный путь, либо оформить как отдельный не-thesis режим вне `G0–G3`.
- Добавить отсутствующий seed/template для `G3`.
- Добавить regression-тесты на изоляцию вкладов `G0`, `G1`, `G2`, `G3`.

### Артефакты завершения

- тесты, гарантирующие, что `G1` и `G2` не открывают collegial review.

## 3. Приведение коллегиального review к требованиям главы

### Артефакты завершения

## 4. Приведение action-модели к главе

### Цель

Снять противоречие между тезисом главы о чистом freeform-подходе и текущим hybrid runtime.

### Принятое решение

Источник истины для этого пункта: глава 2.

Код должен быть приведён к модели:

- убрать фиксированное меню как основной путь;
- оставить `perform` основным действием;
- structured actions использовать только как внутренний слой арбитра, а не как интерфейс агента;
- снять permission-gating с базовой коммуникации.

### Практическая интерпретация

- агент должен описывать намерение в свободной форме;
- арбитр может по-прежнему раскладывать это намерение на детерминированные внутренние `StateOp`;
- typed operations остаются внутренним исполнительным слоем, а не пользовательским интерфейсом когнитивного агента;
- коммуникация должна ограничиваться физикой мира и видимостью каналов, а не отдельным capability-гейтом.

## 5. Уточнение persona pipeline

## 6. Усиление spatial grounding

### Цель

Перевести пространственную укоренённость из mostly-soft prompt layer в частично enforced runtime physics.

### Задачи

- Явно закрепить, что `zone:*` и связанные средовые сущности являются first-class частью физики мира, а не только prompt-layer контекстом.
- Определить минимальный hard-rule набор для коммуникации:
  - приватный контакт только при совместимой локации/зоне или через явно существующий канал;
  - публичная коммуникация через `chan:*` / `org:*` как отдельный случай.
- Проверить structured actions на bypass пространственных ограничений.
- Сузить agent prompt от полного списка typed-id к реально релевантному подмножеству сущностей.
- Добавить тесты на невозможность приватного контакта без пространственного пересечения.

### Артефакты завершения

- runtime-правила, соответствующие тезису о spatial co-presence;
- менее “всеведущий” prompt агента.
