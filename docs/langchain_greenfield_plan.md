# План: greenfield-ветка на LangChain/LangGraph для MAGISTRY

Ветка: `feat/langchain-greenfield`.

Этот план **не про миграцию** текущего `magistry_sim`, а про новую реализацию “с нуля” (с возможным переиспользованием удачных компонентов вроде JSONL-трассировки).

> **[Р]**: Решение «с нуля» оправдано масштабом проблем, но стоит явно указать, какие компоненты текущего движка переиспользуются помимо JSONL-трассировки. Уже есть рабочие вещи: Pydantic-схемы `StateOp` (16 типов в `state_ops.py`), `EventLog` (`events.py`), `Case`/`Proposal`/`Vote` (`cases.py`), `ReputationRecord` (`reputation.py`). Писать их заново — потеря времени. Переиспользование этих модулей не противоречит «greenfield», если импортировать их как библиотеку.

Основание: заметки по прогону S2/G2 (`results/S2_G2_seed42_analysis.md`), ключевые проблемы:
- вторичные агенты и внешние сущности должны появляться из “мира”, а не фиксированным числом;
- провайдер/скорость/параллелизм;
- управление контекстом (память, суммаризация, дедупликация);
- фантомные адресаты/цели (сообщения и действия “в пустоту”);
- репутация/должности должны быть прозрачными и не применяться к внешним сущностям;
- `s2_g2_enriched.json` не должен быть набором хардкодов (needs/schedule/resources/governance/etc.).

> **[Р]**: Список проблем корректный, но не расставлены приоритеты. По данным S2/G2 (7.5M токенов, 5.2 часа, 25 раундов) главный удар по бюджету — арбитр (67.6% токенов, 5.1M). Вторая по весу проблема — 8–10 LLM-вызовов на ход агента (1718 вызовов при 225 ходах). Фантомы (31% сообщений) критичны для валидности, но не для стоимости. Приоритизация нужна, чтобы не тратить 3–7 дней на ScenarioCompiler (M5), пока арбитр продолжает съедать 70%.

## 0) Цели и инварианты

### Цели (must-have)
1. **Жёсткая причинность мира**: нельзя “написать NGO_1” приватно, если сущности нет в реестре мира.
2. **Контекст под контролем**: у каждого LLM-вызова есть бюджет токенов и стратегия компрессии (summary/retrieval).
3. **Параллелизм по умолчанию**: независимые шаги разных агентов исполняются конкурентно.
4. **Измеримость**: события/промпты/ответы пишутся в JSONL; оракул и метрики работают чанками, без “загрузить всё”.
5. **Разделение “внутренние/внешние”**: репутация/карьера только для внутренних участников системы.
6. **Репутация без “минусов”**: публичная репутация не уходит ниже 0 (нижняя граница), старт по умолчанию — 0.
7. **Должности только через ДАО**: изменение должности (promotion/demotion) происходит только через явное голосование (и только если агент согласен), иначе — no-op.

> **[Р]**: Цели 1–5 — точные и обоснованные экспериментом. Цель 6 (пол на нуле) решает конкретную проблему: в S2/G2 `off_1` упал до 4.7, `fam_1` до 7.8, при этом числа были непрозрачны для агентов. Пол на нуле разумен.
>
> Цель 7 (ДАО для должностей) — проблемна. В S2/G2 `cand_2` слетела с «директора департамента» (53.9) до «заместителя начальника» (31.0) за два раунда без явного события `position_demoted`. Реальная проблема — отсутствие логирования демоушена, а не отсутствие голосования. Полноценный механизм ДАО (голосование + согласие агента) — отдельная подсистема, которая: (а) не решает главные дефекты прогона, (б) вводит новую сложность (кворум, порядок голосования, тайм-ауты), (в) не имеет аналога в реальных бюрократических системах, которые симулируются. Достаточно: явное событие `position_changed` с указанием причины, логируемое в `events.jsonl`.

### Инварианты (из AGENTS.md/архитектуры)
- Движок не знает предметной области; специфика — в сценариях/конфигах.
- Полномочия (`Capability`) важнее “ролей”.
- Когнитивный цикл Park et al.: observe → memory → reflection → planning → action.
- Числа скрыты от LLM (LLM видит текстовые описания).

> **[Р]**: Инвариант «когнитивный цикл Park et al.» закрепляет 5-шаговый цикл с отдельными LLM-вызовами на рефлексию и планирование. Это прямое противоречие ключевой цели «контекст под контролем» и задаче снижения стоимости. В S2/G2 текущий цикл (8–10 вызовов на ход) генерирует 1718 agent-вызовов за 25 раундов. Если заменить его единым вызовом с `ConversationSummaryBufferMemory` (агент-как-диалог), получится 225 вызовов — снижение в 7.6 раза. Park et al. описывают архитектуру для исследовательской статьи с безлимитным контекстом OpenAI; у нас ограничения по бюджету и задержке реальные. Предлагаю не закреплять 5-шаговый цикл как инвариант, а считать его конфигурируемым: для экспериментов с дешёвой моделью — один вызов, для детального анализа — полный цикл.
>
> Инвариант «числа скрыты от LLM» — хороший принцип, но в текущем коде (`context.py:build_situation`) агентам передаётся `reputation_score` и числовые `resources`. Нужно не просто декларировать, а обеспечить: ни один промпт не содержит float-значений репутации.

## 1) Технологическое решение (выбор пакетов)

Минимальный стек LangChain (без “зоопарка”):
- `langchain-core`: LCEL (Runnable), базовые типы.
- `langchain-openai`: ChatOpenAI/OpenAIEmbeddings с OpenAI-compatible API (OpenRouter/и т.п.).
- `langchain-community`: ретриверы/векторсторы (FAISS/Chroma/BM25 и т.п.) — только если нужно.

Оркестрация (рекомендуется):
- `langgraph`: граф состояний для когнитивного цикла и world step’ов (с явным state).

> **[Р]**: Набор пакетов корректный, но неполный. Для персистентности чекпоинтов нужен `langgraph-checkpoint-sqlite` (или `-postgres`). Для `ConversationSummaryBufferMemory` нужен основной `langchain`. Если plan сохраняет 5-step цикл с vector retrieval, `langchain-community` становится обязательным, а не «только если нужно», плюс потребуется `faiss-cpu` или `chromadb`.

Важное: LangChain — это **инфраструктура цепочек**, а не замена физики мира. “Физика мира” остаётся в нашем WorldState + apply_ops.

> **[Р]**: Верное разделение. `apply_ops` из `state_ops.py` (16 типов `StateOp`, детерминированное применение) — одна из работающих частей текущего движка. Её нужно переиспользовать как есть.

## 2) Архитектура greenfield-движка (предлагаемая)

### 2.1. Сущности
- `WorldState`: единый источник истины (агенты, сущности, артефакты, коммуникации, ресурсы, расписание, репутация).
- `EntityRegistry`: реестр сущностей мира с типами:
  - `Agent` (internal/external),
  - `Org/Channel/Public` (явные “внешние” адресаты),
  - `WorkItem` (универсальный объект процесса: дело/проект/задача; “cases” — частный вид workitem),
  - `Artifact` (доказательство/документ/публикация).
- `EventLog` (JSONL): каждое применённое изменение — событие (не только LLM calls).

> **[Р]**: `EntityRegistry` — ключевая новая абстракция, и она правильная. Но план не отвечает на критические вопросы жизненного цикла:
>
> 1. Кто создаёт сущности в runtime? В S2/G2 агенты «выдумывали» tech_co_1, ngo_1, journalist_1 (28 уникальных фантомов). Если только world-gen может создавать сущности — это правильно, но тогда нужен механизм «запроса на создание» от кого-то.
> 2. `Artifact` — новый тип, не существующий в текущем коде. Какие операции с ним предполагаются? Если это `evidence` из текущего `AddEvidenceOp`, достаточно расширить существующую систему.

### 2.2. Действия
- Агент возвращает **структурированный** список действий (Pydantic-схема), с обязательными полями:
  - `action_type` (enum),
  - `target_id` (строго из registry, либо пусто),
  - `params` (ограниченный набор).
- “Свободные действия” возможны, но:
  1) проходят pre-validator (существование целей, базовые ограничения),
  2) затем LLM-арбитр решает допустимость и выдаёт `StateOp[]`.

> **[Р]**: Двухступенчатая валидация (pre-validator + LLM-арбитр) — отличное решение. Pre-validator отсекает фантомные `target_id` до того, как тратить токены арбитра. В S2/G2 ~29% одобренных действий имели target, не являющийся ни `agent_id`, ни `case_id` (234 из 809). Pre-validator убрал бы их за ноль токенов.
>
> Проблема: `action_type` как enum противоречит инварианту «движок не знает предметной области». Текущие действия в `tools/actions.py` — это `open_case`, `submit_proposal`, `cast_vote`, `file_report`. Они предметно-специфичны. Если зашить их в enum движка, движок становится привязан к «бюрократической» области. Альтернатива: `action_type` задаётся сценарием, а движок работает с произвольными типами (как сейчас с `perform_action`). Structured output LangChain поддерживает динамические enum через Pydantic `Literal` из конфига.
>
> Отсутствует лимит на количество действий за ход. В S2/G2 `cand_2` подала 56 предложений — нет причины не ограничить до 2–3 действий за ход.

### 2.3. Контекст и память
- Память агента = набор `Document` с метаданными (kind, time, importance, entities).
- Retrieval = ансамбль:
  - time-weighted vector retriever,
  - BM25 по тексту.
- Summarization включается **рано** и регулярно:
  - дедупликация “почти одинаковых” записей,
  - TTL/архив для низковажных деталей,
  - отдельный “executive summary” состояния агента.

> **[Р]**: Это описание на ~80% повторяет текущий `MemoryStream` из `memory.py`. Сравнение:
>
> | Свойство | Текущий MemoryStream | Этот план |
> |---|---|---|
> | Хранение | `MemoryRecord` с importance, kind, embedding | `Document` с kind, time, importance, entities |
> | Retrieval | 0.5×recency + 2.0×cosine + 1.5×bm25 + 2.0×importance | time-weighted vector + BM25 |
> | Суммаризация | `summarize_old()` — LLM сжимает пакет в 3–5 фактов | «рано и регулярно» (без механизма) |
> | Дедупликация | Нет | Заявлена, но без описания метода |
> | TTL/лимит | `max_records=500`, вытесняет старые | TTL/архив (без конкретики) |
>
> Налицо риск «переизобрести MemoryStream» с другими именами. Главная проблема памяти из S2/G2 — не устройство retrieval, а то, что результаты отклонённых действий не попадают в память (off_1 трижды пытается открыть D-001). Это решается одной строкой: `memory.add_observation(f”Действие отклонено: {reason}”)`.
>
> Альтернативный подход, обсуждавшийся ранее: `ConversationSummaryBufferMemory` из LangChain. Агент — непрерывный диалог: недавние сообщения хранятся дословно, старые автоматически суммаризируются при превышении `max_token_limit`. Это решает и суммаризацию, и дедупликацию, и TTL — без кастомного кода. Один LLM-вызов на ход вместо пяти. В плане этот подход не рассмотрен вообще.

### 2.4. Оркестрация (LangGraph)
Один “узел” графа = один атомарный шаг цикла, с жёсткими входами/выходами.

`AgentGraph`:
1) observe (приём событий/сообщений)
2) update_memory (embed + store + dedup)
3) reflect (по порогу)
4) plan (strategic/tactical)
5) act (генерация действий)

> **[Р]**: AgentGraph с 5 узлами — это 3–5 LLM-вызовов на ход (reflect и plan могут быть пропущены). При 9 агентах и 25 раундах: минимум 9 × 25 × 3 = 675 agent-вызовов. В S2/G2 было 1718 — экономия ~60%, но не порядок. Для сравнения, подход «один вызов на ход» (ConversationSummaryBufferMemory): 9 × 25 = 225 вызовов — экономия 87%.
>
> Узлы `update_memory` (embed + store + dedup) и `reflect` требуют эмбеддингов — это значит, нужен embedding-провайдер. Через OpenRouter эмбеддинги работают не напрямую; нужен либо отдельный провайдер (OpenAI API, sentence-transformers локально), либо отказ от vector retrieval в пользу диалоговой памяти.
>
> Критично: узел `observe` и `update_memory` — это не LLM-вызовы, а механические операции (приём событий, запись в store). Делать их «узлами графа» в LangGraph — оверинжиниринг. LangGraph-узел оправдан, когда внутри LLM-вызов или асинхронная операция. Для механики достаточно обычной функции.

`WorldGraph` (на тик/раунд):
1) собрать действия всех агентов (параллельно)
2) валидация/арбитраж (параллельно на снапшоте + затем детерминированное применение)
3) применить ops (последовательно, детерминированно)
4) внешние события мира (world-gen) без “подглядывания” промптов
5) обновить метрики/оракул чанками

> **[Р]**: WorldGraph описан верно. Шаг 2 «параллельная валидация на снапшоте» — хорошая идея, но требует осторожности: если два агента одновременно пытаются, например, закрыть одно дело, параллельная валидация одобрит оба, а последовательное применение сломается на втором. Нужен механизм конфликт-детекции при merge (или пессимистическая блокировка по `target_id`).
>
> Шаг 4 «world-gen без подглядывания промптов» — прямое решение проблемы P0 из независимого анализа. В S2/G2 world_generator получал `llm_call` с системными промптами агентов. Здесь это исправлено.

## 2.5. Контекст-менеджмент (вдохновение: codex-sdk)

Задача: не “накручивать память”, а держать её управляемой и воспроизводимой.

Минимальные требования:
- **Явные бюджеты**: `max_prompt_tokens` на каждый node (observe/reflect/plan/act/arbiter).
- **Слои памяти**: `working` (последние события), `episodic` (важные эпизоды), `summary` (executive state).
- **Дедуп**: схлопывание повторяющихся планов/рефлексий/”попыток” в один факт с счётчиком.
- **Feedback loop**: отказ арбитра и причина отказа — обязательная запись в память как “это уже пробовали / нельзя”.
- **Масштабируемый retrieval**: поиск только по релевантным сущностям + времени (entity/time filtered retrieval), а не “всё подряд”.

> **[Р]**: Раздел с правильными намерениями, но без конкретики реализации.
>
> **Явные бюджеты** — самое ценное нововведение. В S2/G2 промпт арбитра рос с 1562 до 6050 токенов (4x за 25 раундов), а промпт `fam_2` достиг 11038 токенов на R20. Бюджет должен быть жёстким: если контекст превышает лимит, обрезается до лимита. Вопрос: что обрезается? Нужна приоритизация (system prompt неприкосновенен, затем последние события, затем memory retrieval).
>
> **Слои памяти** — три слоя описаны, но `ConversationSummaryBufferMemory` решает это автоматически: `working` = недавние сообщения (дословно), `summary` = суммаризация старых (LLM-компакция). Слой `episodic` требует отдельного vector store, что возвращает к сложности MemoryStream.
>
> **Дедуп** — обязателен. В S2/G2 `off_1` имел один и тот же план в 5 последовательных раундах, а cand_2 подала 56 предложений с тремя уникальными содержаниями. Метод дедупа не описан: порог cosine similarity? Точное совпадение первых N символов? LLM-вызов? Каждый метод имеет свою стоимость.
>
> **Feedback loop** — критичнейший пункт. В текущем коде `cognitive_runner.py` результат арбитра не записывается в `MemoryStream`. Это одна из двух главных причин зацикливания (вторая — дедуп). Реализация тривиальна, не требует нового движка.
>
> **Отсутствует** механизм контекст-менеджмента для арбитра — а это 67.6% токенов. Подход «YAML-журнал в памяти арбитра» (арбитр ведёт инкрементальный журнал мира вместо получения полного дампа на каждый вызов) решает проблему радикально. В плане арбитр упомянут через `max_prompt_tokens`, но стратегия не описана.

- Создать новый пакет (например, `src/magistry_lc/`) и CLI “песочницу”.
- Определить Pydantic-схемы `Action`, `StateOp`, `Event`.
- JSONL лог: `events.jsonl`, `trace.jsonl` (LLM spans) — единый формат.

**Готово, если:** CLI запускается и пишет пустой `events.jsonl` на 1 “тик”.

> **[Р]**: `StateOp` уже определён в `state_ops.py` (16 типов: `CreateCaseOp`, `ModifyReputationOp`, `SendMessageOp` и т.д.), `Event` — в `events.py`, `EventLog` — там же, JSONL формат — работает. «Определить Pydantic-схемы» = импортировать существующие. Если цель — новый пакет `src/magistry_lc/`, достаточно сделать его зависимым от `magistry_sim.state_ops` и `magistry_sim.events`. Переписывание этих модулей «с нуля» без изменения семантики — бессмысленная работа.

### M1 — EntityRegistry + запрет фантомов (2–4 дня)
- Реестр сущностей, типизация `target_id`.
- Pre-validator, который режет/нормализует попытки “в пустоту”.
- Базовые адресаты `public`, `official_channel`, `org_x` — только если заведены в registry.

**Готово, если:** phantom-message ratio = 0 на smoke-тесте.

> **[Р]**: Правильный приоритет. 2–4 дня — адекватная оценка. Но: `EntityRegistry` как отдельный компонент — это по сути `dict[str, EntityType]` + валидатор. Реализуется за полдня. Основная работа — интеграция в арбитра (чтобы `evaluate()` проверял target до LLM-вызова) и в `_deliver_observations()` (чтобы `send_message` к несуществующему ID возвращал ошибку агенту). Если делать это в текущем движке, потребуется ~100 строк изменений в `arbiter.py` и `environment.py`. Если делать «с нуля» — те же 100 строк в новых файлах.

### M2 — AgentGraph v0 (3–6 дней)
- Observe/memory/retrieve/act без рефлексии (минимум).
- Memory: vector store + простая суммаризация.
- Действия: structured output + строгая схема.

**Готово, если:** 1 агент стабильно действует 10 тиков без роста контекста > заданного бюджета.

> **[Р]**: Критерий приёмки хороший — измеримый и конкретный. Но 3–6 дней — это срок, сравнимый с полной реализацией альтернативного подхода (ConversationRunner поверх ConversationSummaryBufferMemory — ~200 строк, 1 день). Вопрос приоритетов: стоит ли тратить неделю на vector store + суммаризацию + dedup + retrieval, когда LangChain предоставляет готовый `ConversationSummaryBufferMemory`, который автоматически суммаризирует старые сообщения и не требует эмбеддингов? Если ответ «да, нужна гранулярная память» — нужно обосновать, для каких задач retrieval по вектору лучше, чем хронологическая суммаризация.

### M3 — Arbiter v0 с контекст-компрессией (4–8 дней)
- Арбитр получает **не дамп мира**, а релевантный снапшот (entities + workitems, связанные с действием).
- Стандартизировать `StateOp` и применение.

**Готово, если:** доля токенов арбитра < 30–40% на мини-сценарии.

> **[Р]**: Это самый важный milestone (67.6% токенов = арбитр), и ему уделено наименьшее внимание — 2 строки без описания механизма. «Релевантный снапшот» — как определяется релевантность? Варианты:
>
> 1. **Правило на основе target**: если действие направлено на `off_2`, арбитру передаётся профиль `off_2` + связанные дела + 1-hop соседи в графе. Дёшево, детерминированно, но может пропустить контекст.
> 2. **YAML-журнал (рекомендуется)**: арбитр — долгоживущий агент с `ConversationSummaryBufferMemory` (порог 80K токенов). Ведёт YAML-документ мира инкрементально. На каждое действие получает только описание действия — весь контекст уже в памяти диалога. Автоматическая суммаризация старых решений.
> 3. **LLM-retrieval**: отдельный вызов для выбора релевантного контекста — ещё один LLM-вызов сверху.
>
> Plan не выбирает ни один из этих подходов. «Стандартизировать StateOp» — уже сделано, 16 типов в `state_ops.py`. Оценка 4–8 дней при отсутствии чёткого дизайна — скорее 8+.
>
> Критерий «< 30–40%» — мягкий. При подходе с YAML-журналом арбитр использует ~0 дополнительных токенов на передачу контекста (всё в памяти), цель реалистичнее: < 20%.

## 4) Риски и анти-паттерны

- **Зависимость от “магии LangChain”**: не полагаться на memory-модули без явных бюджетов/инвариантов.
- **Слишком ранний “agent executor”**: LangChain Agents часто ломают причинность мира. Лучше — structured output + наш apply_ops.
- **Без реестра сущностей** любой LLM снова создаст фантомов.
- **Авто‑промоушены/демоушены без ДАО**: любые изменения должности должны быть отдельным механизмом (vote + consent), иначе метрики будут “ломаться”.
